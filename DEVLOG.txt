一、技术栈
================================================================================

【后端】
  * FastAPI + Uvicorn        HTTP API + WebSocket 实时链路，asyncio 并发
  * MediaPipe PoseLandmarker  33 关键点姿态估计 + 人物分割掩码
                              BlazePose，VIDEO 模式，单引擎串行共享
  * OpenCV (headless)         视频解码、帧处理、掩码缩放与 PNG 编码
  * numpy                     关键点与掩码数组运算
  * imageio-ffmpeg            内置 ffmpeg：H.264 转码、截封面、NVENC 硬件编码
  * python-multipart          上传表单解析
  * asyncio / struct          异步写入队列；masks.bin 二进制协议
                              （每帧 uint32 长度 + PNG 字节）

【前端】（零框架、零构建）
  * 原生 ES Modules           模块划分：app / live / replay / pose / api
  * Canvas 2D                 骨架绘制、掩码着色、跨视角仿射映射
  * getUserMedia              摄像头采集（640x480 JPEG q0.6，多设备兜底）
  * WebSocket 二进制帧        实时推理链路，2 帧在途流水线
  * HTMLVideoElement          教学视频播放、倍速、片段定位
  * 自研 LRU 缓存             回放帧图片、掩码 ImageBitmap 预解码复用

【部署 / 工程】
  * Dockerfile + docker-compose（Caddy 反向代理）
  * Windows start.bat 一键启动
  * .env.example 环境变量模板

【数据流】
  摄像头 --JPEG--> FastAPI --> MediaPipe（33 关键点 + 96x96 掩码）
                              |
                              +--> PoseStabilizer（漂移剔除/平滑/补帧）
                                        |
        录制：24fps 配额采样 <-----------+
                |
        frames/*.jpg + masks.bin + poses.json
                |
        纠错回放 <-- Canvas 着色（人物阴影 + 骨架）

  上传视频 --> ffmpeg 转 H.264 --> 15fps 采样 --> pose.json + masks.bin

二、技术选型决策
================================================================================

  方案                       结论    原因
  --------------------------------------------------------------------------
  SAM3 视频分割              否决    CPU 单帧数秒、权重数 GB，撑不住 25fps
  YOLO-seg                   否决    额外约 2GB 依赖，CPU 单帧 100-300ms
  MediaPipe 自带人物分割     采用    与骨架同一次推理输出剪影，零额外模型，
                                     零额外依赖，实测仅 +6.5ms
  MediaPipe GPU delegate     暂缓    Windows + Python 下不稳定，易静默回退；
                                     当前瓶颈不在推理
  浏览器内 WebGL 推理        暂缓    需重构整条链路（服务端推理 -> 前端推理）

三、Bug 清单（13 项）
================================================================================

[1] 微信视频上传后浏览器黑屏
    根因：源为 HEVC 编码，Chrome 无法解码
    修复：ffmpeg 统一转 H.264 + AAC、+faststart、yuv420p

[2] 上传完成后前端 JS 报错
    根因：渲染了不存在的轮播容器
    修复：移除无效渲染分支

[3] 聊天记录是假的演示数据
    根因：硬编码占位内容
    修复：改为随上传视频生成的真实学习会话

[4] 部分电脑摄像头直接不可用
    根因：首个设备是打不开的虚拟设备，失败即整体放弃
    修复：逐设备尝试兜底，跳过失败设备并给出分类提示

[5] 轮播轨道撑宽页面、标题截断、分页错位
    根因：CSS 溢出 + 滚动容器宽度计算错误
    修复：轨道内滚动、整页翻动、标题换行截断、自动定位

[6] 骨架分析未完成时打开页面，骨骼对比永久丢失
    根因：一次性加载，无重试机制
    修复：切回跟练页自动补载

[7] 半身入镜时骨骼对比整体消失
    根因：髋部不可见导致人体尺度计算失败
    修复：髋部不可见时用肩宽降级估算

[8] 跨视角轮廓左右相反（镜像感）
    根因：教学视频是正向视角、摄像头是镜像显示，映射未做翻转
    修复：三处映射统一先做 x -> 1-x 水平翻转

[9] 骨架抖动、偶发漂移到画面外、短暂丢人
    根因：无稳定层，逐帧原始输出
    修复：PoseStabilizer —— 漂移帧剔除 + 逐点钳制 +
          自适应平滑 + 丢帧补齐

[10] 稳定器漂移检测失效（自研过程引入）
     根因：33 点全局中位数被大量静止/低可见度点稀释成 0
     修复：只对 13 个核心关节（头/肩/肘/腕/髋/膝/踝）取中位数

[11] 录制回放只有 8.8fps
     根因：三重叠加
           ① 录制等推理回包（串行）
           ② 硬节流"上次时间 + 固定间隔"在 30->24fps 时系统性丢一半帧
           ③ 前端仅 1 帧在途
     修复：录制与推理解耦 + 累积配额采样 + 2 帧在途

[12] 人物阴影铺满整个画面
     根因：灰度 PNG 的形状信息在亮度通道，而 Canvas source-in
           合成只认 alpha -> 整帧不透明被整体染色
     修复：后端改存 RGBA（RGB 全白、A=掩码）

[13] 回放时阴影持续闪烁
     根因：顺序播放每帧掩码 key 都不同 -> LRU 命中率为 0；
           异步解码跟不上 24fps -> 解不出的帧跳过阴影
     修复：预解码后续 36 帧 + 缓存容量 180->600 +
           未就绪沿用上一帧轮廓 + 暂停时补画

六、已知限制 / 后续可选方向
================================================================================

  1. 录制帧率受机器负载影响（实测 18-22fps），非满载时达不到 24 上限。
  2. 录制掩码相对画面滞后约 1 帧：推理与录制解耦的固有代价，快速动作时
     轮廓可能轻微滞后（不是闪烁）。可选：相邻帧轮廓插值。
  3. 骨架推理仍在 CPU（单帧 18-28ms）。上 GPU 需 MediaPipe GPU delegate
     （Windows 下不稳定）或改浏览器内 WebGL 推理（架构级改动）。
  4. 旧录制无掩码：早期回放只有骨架，自动降级，不回填。
  5. 实时链路为单引擎串行，多标签页同时跟练会互相排队。
